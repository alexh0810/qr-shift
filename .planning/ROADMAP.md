# Roadmap: QRShift

## Overview

This roadmap turns QRShift from a functional attendance demo into a sharper product demo with a clear public face, a recognizable brand system, and polished core workflows. The milestone stays tightly focused on clarity, conversion, and trust so the product looks and feels ready for customer conversations without expanding into a heavier platform build.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions if needed later

- [ ] **Phase 1: Brand Foundation** - Define QRShift's visual language and shared UI primitives
- [ ] **Phase 2: Landing Page** - Ship a public-facing homepage that explains the product fast and drives contact
- [ ] **Phase 3: Product Rebrand** - Apply the new identity and usability polish to the core demo flows
- [ ] **Phase 4: Demo Release** - Validate the polished experience and prepare it for private demo sharing

## Phase Details

### Phase 1: Brand Foundation
**Goal**: Establish the brand language and reusable interface foundation for the rest of the milestone.
**Depends on**: Nothing (first phase)
**Requirements**: [BRAND-01, BRAND-03]
**UI hint**: yes
**Success Criteria** (what must be TRUE):
  1. Shared visual foundations exist for color, typography, spacing, and reusable UI patterns.
  2. New UI work can reuse those patterns without redefining style decisions screen by screen.
  3. The selected direction feels clean, operational, and recognizably QRShift in implemented primitives or reference surfaces.
**Plans**: 3 plans

Plans:
- [ ] 01-01: Define the QRShift brand direction, design tokens, and component rules
- [ ] 01-02: Refactor shared styling entry points to support the new visual system
- [ ] 01-03: Document how the new patterns should be used across future screens

### Phase 2: Landing Page
**Goal**: Ship a landing page inside the existing app that explains QRShift quickly and converts visitors into demo or contact actions.
**Depends on**: Phase 1
**Requirements**: [MKTG-01, MKTG-02, MKTG-03, MKTG-04, UX-03]
**UI hint**: yes
**Success Criteria** (what must be TRUE):
  1. A first-time visitor can understand what QRShift does and who it is for within 10 seconds.
  2. The homepage clearly highlights the core product value and ideal customer fit.
  3. Visitors can request a demo through Calendly from the homepage.
  4. Visitors can contact the founder through the email call-to-action.
**Plans**: 3 plans

Plans:
- [ ] 02-01: Create the landing page content structure and messaging hierarchy
- [ ] 02-02: Implement the homepage sections, responsive layout, and conversion CTAs
- [ ] 02-03: Connect the landing page cleanly to the product demo entry points

### Phase 3: Product Rebrand
**Goal**: Apply the new QRShift identity and UX polish across the demo app without breaking core attendance and reporting behavior.
**Depends on**: Phase 2
**Requirements**: [BRAND-02, UX-01, UX-02]
**UI hint**: yes
**Success Criteria** (what must be TRUE):
  1. The scan, dashboard, reports, and admin screens remain functional after the redesign.
  2. Core product surfaces feel visually consistent with the landing page and shared design system.
  3. The app remains clear and usable on both mobile and desktop after the refresh.
**Plans**: 4 plans

Plans:
- [ ] 03-01: Refresh shared layout, navigation, and cross-app presentation patterns
- [ ] 03-02: Rework the scan flow and success states with the new identity
- [ ] 03-03: Redesign dashboard and reporting surfaces for clarity and consistency
- [ ] 03-04: Polish admin and demo setup screens plus empty and error states

### Phase 4: Demo Release
**Goal**: Make the product coherent and trustworthy enough for private customer and investor demos.
**Depends on**: Phase 3
**Requirements**: [DEMO-01, DEMO-02]
**UI hint**: yes
**Success Criteria** (what must be TRUE):
  1. The journey from landing page to product demo feels coherent, polished, and trustworthy.
  2. A concise QA checklist validates landing CTAs, QR clocking, dashboard behavior, reports, and export flows.
  3. The release is stable enough to share privately with prospects without obvious demo-breaking issues.
**Plans**: 2 plans

Plans:
- [ ] 04-01: Run end-to-end demo QA and fix the highest-impact polish issues
- [ ] 04-02: Finalize release copy, demo checklist, and private-share readiness
