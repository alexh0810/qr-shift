## User Constraints (from CONTEXT.md)

### Locked Decisions
## Implementation Decisions

### Manager authentication
- **D-01:** Manager dashboard and reports access must be validated by a trusted server boundary, not by fetching the store PIN into browser code and comparing it client-side.
- **D-02:** Keep the manager UX simple: managers still enter a store PIN, but the PIN is submitted to a server route for validation.
- **D-03:** A successful manager PIN check should create a server-issued session, preferably an HttpOnly cookie scoped to the store/QR token, so users do not need to re-enter the PIN constantly.
- **D-04:** The browser should not receive the store PIN during normal store lookup.
- **D-05:** Store PINs should not remain plaintext long term. Prefer storing a hash for new/updated stores; if migration is needed, keep it minimal and compatible with existing demo records.

### Employee scan flow
- **D-06:** Employees should remain account-free for V1. Do not introduce employee login, staff passwords, or account management in this phase.
- **D-07:** The scan route can keep the current "choose your name, confirm clock action" flow.
- **D-08:** Clock actions must be validated server-side before writing a timelog: QR token maps to a store, selected employee belongs to that store, requested action is a valid transition, and duplicate/race-prone submissions are rejected or safely handled.
- **D-09:** Employee PINs are deferred. They may be considered later only if real customer use shows identity abuse or buddy-punching risk.

### Admin and owner-only setup
- **D-10:** `/admin/create-store` must become owner-only before private demos. It should not be possible for anyone who discovers the URL to create unlimited stores, employees, or demo timelogs.
- **D-11:** For this stage, a simple owner gate is acceptable: environment-backed owner secret, server-side check, or equivalent lightweight protection.
- **D-12:** Do not build multi-admin accounts, organization management, invitations, or billing in this phase.

### Firestore and server boundary
- **D-13:** Sensitive operations should move away from direct browser Firestore writes where practical. Use Next.js route handlers or another trusted Firebase-compatible boundary for manager PIN validation, clock actions, and owner-only store creation.
- **D-14:** Firestore rules should be made explicit and checked into the repo if the phase touches read/write enforcement. Rules should at minimum prevent broad unauthenticated writes and constrain timelog/store/employee fields.
- **D-15:** Existing Firebase/Next.js architecture should remain. Do not introduce a separate backend service, microservice, or heavyweight auth provider unless research proves it is necessary.

### Product simplicity
- **D-16:** Security improvements must not make QRShift feel complex for small businesses. The final user-facing flow should still feel like: scan, pick name, clock in/out; manager enters PIN; owner creates store.
- **D-17:** Prefer clear, minimal error states over educational security copy. Users should know what to do next, not read a security explanation.
- **D-18:** The target security level is "safe private demo / early pilot," not enterprise payroll compliance.

### Claude's Discretion
- Choose the exact implementation mechanism for cookie signing, PIN hashing, session expiration, API route names, and Firestore rule shape, as long as the decisions above are satisfied.
- Decide whether Phase 03.1 should be split into multiple plans during planning if the work is too large for one safe execution pass.

### Deferred Ideas (OUT OF SCOPE)
- Full user accounts for managers and staff.
- Role-based permissions, account management, invitations, and password recovery.
- Employee PINs or staff identity verification beyond name selection.
- Billing, subscriptions, Stripe, payroll integrations, and multi-tenant admin dashboards.
- Enterprise compliance, audit logs, and advanced payroll approval workflows.

## Summary

QRShift should add a minimal trusted boundary inside the existing Next.js App Router application, not a separate backend or full auth provider. [VERIFIED: AGENTS.md + CONTEXT.md] Next.js 14 route handlers are available under `app` and support request methods including `GET` and `POST`, so they fit the current architecture for manager login/session checks, clock actions, and owner-gated admin creation. [CITED: https://nextjs.org/docs/14/app/building-your-application/routing/route-handlers]

Use `firebase-admin` only from server-only modules and route handlers for sensitive reads/writes. [CITED: https://firebase.google.com/docs/admin/setup] Firestore Security Rules evaluate web client SDK requests, while server client libraries bypass rules and authenticate through Application Default Credentials or service-account credentials, so server code must enforce authorization explicitly. [CITED: https://firebase.google.com/docs/firestore/security/get-started]

**Primary recommendation:** Add `firebase-admin`, `src/lib/firebase-admin.ts`, `src/lib/server-auth.ts`, and scoped `app/api/.../route.ts` handlers; keep scan UX unchanged but move clock writes and manager/admin validation server-side. [VERIFIED: codebase + official docs]

### Pattern 1: Trusted Route Handler Boundary

**What:** Put manager PIN validation, owner admin creation, and clock writes behind `app/api/**/route.ts`. [CITED: https://nextjs.org/docs/14/app/building-your-application/routing/route-handlers]

**When to use:** Use for every operation where the browser must not receive secrets or directly decide authorization. [VERIFIED: CONTEXT.md + CODEBASE-REVIEW.md]

**Example:**

```typescript
// Source: Next.js Route Handlers docs + QRShift codebase
export const runtime = "nodejs";

export async function POST(request: Request) {
  const body = await request.json();
  // Resolve qr_token -> store on the server.
  // Validate submitted PIN or owner secret.
  // Return only safe DTOs to the browser.
  return Response.json({ ok: true });
}
```

### Pattern 2: Signed HttpOnly Cookie Session

**What:** Store only a signed, minimal payload such as `{ kind: "manager", storeId, qrToken, exp }` in an HttpOnly, `sameSite: "lax"`, `secure` in production cookie. [CITED: https://nextjs.org/docs/app/api-reference/functions/cookies]

**When to use:** Use after successful manager PIN validation and owner-secret validation so users do not repeatedly enter secrets. [VERIFIED: CONTEXT.md]

**Example:**

```typescript
// Source: Next.js cookies docs + Node 18 crypto docs
import { createHmac, timingSafeEqual } from "node:crypto";

function sign(value: string, secret: string) {
  return createHmac("sha256", secret).update(value).digest("base64url");
}
```

### Pattern 3: Transactional Clock Action

**What:** Server route resolves store and employee, reads latest relevant timelog inside a transaction, verifies expected transition, and writes the new timelog at the end. [CITED: https://firebase.google.com/docs/firestore/manage-data/transactions]

**When to use:** Use for `POST /api/stores/[qr_token]/clock` to prevent stale client state and duplicate tap corruption. [VERIFIED: CODEBASE-REVIEW.md]

**Example:**

```typescript
// Source: Firestore transaction docs + QRShift scan flow
await adminDb.runTransaction(async (transaction) => {
  const employeeSnap = await transaction.get(employeeRef);
  if (!employeeSnap.exists || employeeSnap.get("store_id") !== storeId) {
    throw new Error("invalid_employee");
  }

  // Read latest status marker or latest timelog query result before writing.
  // Reject if requestedAction is not the next valid transition.
  transaction.create(timelogRef, {
    employee_id: employeeId,
    store_id: storeId,
    type: requestedAction,
    timestamp: FieldValue.serverTimestamp(),
  });
});
```

### Pattern 4: Plaintext PIN Compatibility With Hash Upgrade

**What:** New stores write `pin_hash`, not `pin`; existing stores can authenticate once against legacy `pin`, then opportunistically write `pin_hash` and remove or ignore `pin`. [VERIFIED: src/lib/db.ts stores plaintext `pin` today]

**When to use:** Use during Phase 03.1 to avoid a separate manual data migration for demo records. [VERIFIED: CONTEXT.md]

### Anti-Patterns to Avoid

- **Returning raw `Store` to browser:** Current `getStoreByQrToken` returns `pin`; replace with a public DTO that excludes `pin` and `pin_hash`. [VERIFIED: src/lib/db.ts]
- **Using localStorage as authorization:** Current `PinGuard` trusts `store_${qr_token}_unlocked`; replace with server session check. [VERIFIED: src/components/PinGuard.tsx]
- **Blind `addDoc` timelog writes:** Current `addTimelog` appends without transition validation; replace with server-side transaction. [VERIFIED: src/lib/db.ts]
- **Client-side admin seeding:** Current `/admin/create-store` creates stores and seeded timelogs from the browser; move creation to owner-gated route handlers. [VERIFIED: src/app/admin/create-store/page.tsx]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Privileged Firestore access | Custom REST calls with browser credentials | `firebase-admin` server SDK | Official server SDK supports privileged trusted environments. [CITED: https://firebase.google.com/docs/admin/setup] |
| PIN hashing primitive | Plain SHA-256 or reversible encryption | Node `crypto.scrypt` with per-PIN salt and `timingSafeEqual` | Node 18 exposes password KDF and constant-time comparison APIs. [CITED: Node 18 crypto docs] |

## Common Pitfalls

### Pitfall 1: Server SDK Bypasses Rules

**What goes wrong:** Route handlers using Firebase Admin can read/write any document even after strict Firestore rules are added. [CITED: https://firebase.google.com/docs/firestore/security/get-started]

**Why it happens:** Firebase documents that server client libraries bypass Cloud Firestore Security Rules and use IAM/ADC instead. [CITED: https://firebase.google.com/docs/firestore/security/get-started]

**How to avoid:** Keep all authorization checks in `server-auth.ts` and `server-db.ts`, not only in rules. [VERIFIED: architecture recommendation]

**Warning signs:** Route handler accepts `storeId` or `employeeId` from the browser and writes without resolving the QR token/store relationship server-side. [VERIFIED: CODEBASE-REVIEW.md]

### Pitfall 2: Cookie Scope Too Broad Or Too Weak

**What goes wrong:** A manager session for one store unlocks another store or can be forged. [VERIFIED: phase threat model]

**Why it happens:** Cookie payload omits `storeId`/`qrToken` binding or signature verification uses ordinary string equality. [VERIFIED: phase threat model]

**How to avoid:** Include `kind`, `storeId`, `qrToken`, `exp`, and `iat` in the signed payload; verify HMAC with `timingSafeEqual`; reject wrong store or expired sessions. [CITED: Node 18 crypto docs]

**Warning signs:** API routes check only for presence of `manager_session`. [VERIFIED: phase threat model]

### Pitfall 3: Route Handler GET Caching

**What goes wrong:** Session checks or dashboard snapshots can be cached accidentally. [CITED: https://nextjs.org/docs/14/app/building-your-application/routing/route-handlers]

**Why it happens:** Next.js 14 route handlers cache `GET` responses in some cases, while using cookies/headers or non-GET methods opts out. [CITED: https://nextjs.org/docs/14/app/building-your-application/routing/route-handlers]

**How to avoid:** Use cookies in session-sensitive handlers and set `export const dynamic = "force-dynamic"` for session/data routes. [CITED: Next.js route handler docs]

**Warning signs:** `GET /api/manager/session` does not read cookies and does not set dynamic behavior. [VERIFIED: phase design]

### Pitfall 4: PIN Hash Migration Locks Out Demo Stores

**What goes wrong:** Existing demo stores with plaintext `pin` stop working after code expects only `pin_hash`. [VERIFIED: src/lib/db.ts]

**Why it happens:** The current schema has `pin`, not `pin_hash`. [VERIFIED: src/types/index.ts + src/lib/db.ts]

**How to avoid:** Implement dual verification: prefer `pin_hash`, fall back to legacy `pin`, then write `pin_hash` after successful legacy login. [VERIFIED: CONTEXT.md]

**Warning signs:** No branch handles `store.pin` in manager login route. [VERIFIED: phase design]

### Pitfall 5: Firestore Rules Break Employee Scan Reads

**What goes wrong:** Rules block public scan route employee roster reads after sensitive manager writes are moved server-side. [VERIFIED: phase requirements]

**Why it happens:** Employees remain account-free, so public scan metadata still needs carefully constrained unauthenticated reads. [VERIFIED: CONTEXT.md]

**How to avoid:** Either serve scan roster through route handlers or keep read-only rules for QR-token-scoped store metadata and employees while denying client writes. [VERIFIED: Firebase rules docs + phase constraints]

**Warning signs:** Scan page still imports browser `getEmployeesByStoreId` but rules deny all client reads. [VERIFIED: src/app/scan/[qr_token]/page.tsx]
